# JBRS 0.7.2 — audio verification

- Workspace tests: **155 passed, 0 failed**. Coverage includes eight distinct engine profiles, finite bounded output, deterministic rendering across block sizes, stereo siren panning, phase-wrap boundaries, stable vehicle oscillators when distance ordering changes, footstep decay, grounded footstep events, menu muting and incident-only sirens.
- `cargo fmt --all -- --check`, explicit formatting of included sound source, and `cargo clippy --workspace --all-targets -- -D warnings`: passed.
- SDL dummy device: open, bounded queue, pause/clear and resume passed.
- Linux game with SDL disk output: nonzero finite stereo float samples; peak/RMS recorded in `game-signal.json`. Missing-device driver: game continued to a clean exit and logged the audio initialization failure.
- Windows GNU build: passed. SDL queue example and the real game ran through Wine 10.0 with the dummy audio driver; initialization and queue checks passed.
- Host GLES2 + touch controls: real driving scene initialized SDL audio with the dummy driver and completed 60 frames.
- Android 10 ARM64: built as 0.7.2, versionCode 4; APK signature, manifest, CRC and ELF/JNI checks passed. Same preview signing identity.
- The WAV demonstration is generated by the actual game synthesizer: eight engine revs, four footstep surfaces, then siren. Runtime does not load the WAV.

No physical loudspeakers, native Windows 11 audio device, Android handset or target Ironlake hardware were available. Dummy/disk/Wine checks validate the audio pipeline and generated signal, not real-device listening quality or target-hardware performance.

The runtime uses a single bounded SDL queued device with no custom callback thread, no sound file I/O and no allocations inside the synthesizer. Stereo output is 22050 Hz. Audio failure is nonfatal and diagnosed once. `JBRS_AUDIO=0` disables device creation.
